# Лабораторная работа 2: Свой планировщик и где он слепнет

## О чём эта лаба

В первой лабораторной мы искали ошибки многопоточности стресс-тестами: гоняли код миллионы раз в надежде зацепить редкое поведение. Но стресс-тест слеп: он зависит от загрузки ядер, планировщика ОС, гороскопа, погоды и настроения Линуса. Ошибка может воспроизводиться один раз на миллион запусков или исчезнуть при добавлении логирования.

Лестница инструментов поиска конкурентных ошибок:
```
L1: Статический анализ (компилятор, линтеры)
L2: Динамический анализ (TSan / Data Race Detector)
L3: Контролируемый планировщик (свой scheduler, сиды, DFS, bounded preemption)  <-- Эта лаба
L4: Инструмент знает правильный ответ (Lincheck, jcstress)                     <-- Эта лаба (mini-jcstress)
L5: Формальная верификация (TLA+, Spin)
L6: Production (мониторинг, метрики, crash-дампы)
```

В этой работе мы поднимаемся на ступени L3 и L4:
1. Реализуем собственный детерминированный планировщик (L3), который полностью перехватывает управление потоками и превращает недетерминированное исполнение в обход дерева чередований.
2. Проверим на нём сценарии списания (`withdraw`), взаимной блокировки (`transfer`) и упрощённый коллектор с двойной буферизацией из лабораторной 1.
3. Увидим границы L3: где планировщик слепнет из-за пропущенных точек переключения и почему перестановки шагов не ловят переупорядочивания процессора (Store Buffering).
4. Проверим аппаратные эффекты памяти на мини-тесте в стиле jcstress (L4).

## Этап 1. Вытеснение и FirstAlive

Чтобы получить детерминизм, планировщик забирает у ОС право решать, какой поток выполняет следующий шаг.

### Scheduler

`Scheduler` ведёт прогон: запускает потоки, на каждой паузе спрашивает стратегию, кто ходит дальше, и записывает трассу.

Что хранит:
- Потоки и состояние каждого: работает, ждёт хода, ждёт лок или условие, закончил.
- Список `enabled` — потоки, которые могут сделать шаг прямо сейчас.
- Трассу (буквы выбранных потоков: `A`, `B`, …) и лог операций.
- Для правила «без пауз подряд» (раздел «Где Scheduler ставит паузу» ниже): трогал ли поток `Shared`, `SchedLock` или звал `point()` с прошлой паузы.

Что делает:
- `spawn(fn)`: регистрирует поток (`A`, `B`, … по порядку вызова), но сам поток ещё не запускает.
- `point()` и `await(cond)`: вызываются изнутри потока и отдают ход планировщику по правилам пауз.
- `run(strategy)`: запускает зарегистрированные потоки и доводит каждый до первой паузы. Дальше главный цикл:

```
[собрать enabled] -> [strategy.pick] -> [разбудить поток] -> [ждать, пока он отдаст ход]
        ^                                                                   |
        +-------------------------------------------------------------------+
```

Цикл заканчивается, когда все потоки закончили работу или `enabled` пуст при живых потоках (deadlock, этап 2).

### Как поток отдаёт ход
```
Поток A                   Планировщик (Scheduler)              Поток B
  |                                  |                           |
  |-- point() / Shared access ------>|                           |
  |   (A отдаёт ход: sem_sched.rel)  |                           |
  |   sem_A.acquire() [A уснул]      |                           |
  |                                  |-- Strategy.pick() -> B    |
  |                                  |   sem_B.release() ------->| [B проснулся]
  |                                  |                           |-- point()...
  |                                  |<--------------------------| (B отдаёт ход)
  |                                  |-- Strategy.pick() -> A    |
  |<---------------------------------|   sem_A.release()         |
[A проснулся]                        |                           |
```

- У каждого потока свой семафор.
- В любой момент времени бодрствует ровно один поток.
- ОС не может переставить операции местами, так как остальные потоки заблокированы на семафорах. ОС решает лишь, на каком физическом ядре и в какую наносекунду исполнится разрешённый шаг.

### Shared: общая переменная

`Shared<T>` (в C++: `shared<T>`) — обёртка над общей переменной. Внутри обычное значение и имя для лога.

Планировщик может переключить поток только там, где поток сам к нему обратился. Обычное поле (`int balance`) он не видит: чтения и записи идут напрямую, без пауз, и развилок нет. Через `Shared` каждое чтение и запись проходят через планировщик:

```
Обычное поле:  поток A: read -> write   (планировщик не видит, пауз нет)
Shared<T>:     поток A: ⏸ -> get()      (планировщик ставит паузу и развилку)
```

Это не лок: `Shared` никого не блокирует. Синхронизации (мьютексов, CAS, volatile) внутри нет и не нужно: из-за семафоров планировщика в каждый момент работает ровно один поток. Лок, который видит планировщик, — `SchedLock`, этап 2. В `withdraw-v0` баланс — `Shared` без лока; в `withdraw-v1` и `transfer` — обычное поле под `SchedLock`.

Методы:
- `get()` и `set(v)`: перед операцией — пауза по правилам ниже, после — строка в лог: `<имя> -> <значение>` для чтения, `<имя> = <значение>` для записи (например, `A  balance -> 100`, `A  balance = 0`).
- `getAcquire()` и `setRelease(v)` (C++: `get_acquire()` / `set_release(v)`, в заготовке уже сделаны): для планировщика то же, что `get` и `set`. Он перебирает только порядок шагов потоков и не видит эффектов памяти процессора (это пригодится на этапах 6–7).
- `peek()`: чтение без паузы и без лога, для проверок после прогона и условий `await`. Уже есть в заготовке.

Реализовать `Shared<T>` нужно на этом этапе: `get`, `set` (в Java ещё `getAcquire`, `setRelease`).

### Где Scheduler ставит паузу

Пауза — точка, в которой поток отдаёт ход планировщику, а стратегия выбирает, кто пойдёт дальше. Правила ниже — требования к вашей реализации `Scheduler`. Каждая пауза создаёт развилку в дереве расписаний, поэтому от их расстановки зависят все эталонные числа лабораторной.

`withdraw-v1`, стратегия FirstAlive (`./lab2 withdraw-v1 first log`). Символ ⏸ — пауза:

```
            поток A                      поток B                    выбран
   ⏸ 1   mu.lock()                                                    A
         ok = balance >= 100  (true)
   ⏸ 2   mu.unlock()                                                  A
         window()
   ⏸ 3   mu.lock()                                                    A
         balance -= 100       (0)
   ⏸ 4   mu.unlock()                                                  A
         return  — A закончил
   ⏸ 5                                mu.lock()                       B
                                      ok = balance >= 100  (false)
   ⏸ 6                                mu.unlock()                     B
                                      window()
                                      return  — B закончил
```

Столбец «выбран» сверху вниз даёт трассу `AAAABB`. Запуск `./lab2 withdraw-v1 replay AAAABB` повторит её шаг в шаг. У потока B всего две паузы: баланс уже нулевой, условие ложно, и до списания поток не доходит.

Правила расстановки пауз:
- **Операции с общим состоянием.** Пауза ставится перед каждым обращением к `Shared` и `SchedLock`, включая `unlock`. Обычные поля под локом паузу не дают: пока лок захвачен, другой поток до них всё равно не доберётся.
- **Без пауз подряд.** Если с прошлой паузы поток не трогал ничего общего, следующая операция выполняется без паузы.
- **`point()`.** Не меняет данных и не делает паузы перед собой, но считается операцией с общими данными: перед следующей операцией пауза обязательна.
- **Ожидание лока.** Если операция сейчас невозможна (лок занят), поток ждёт и не попадает в список `enabled`, пока лок не освободится.
- **Старт.** `run()` доводит каждый поток до паузы перед его первой операцией, поэтому первый шаг планировщика — уже выбор (⏸ 1 на схеме).
- **Завершение.** Выход из потока тоже передаёт управление планировщику.

`await` пишется на этом этапе, но правило паузы для него описано в этапе 6.

### Стратегия FirstAlive
Всегда выбирает живой поток с минимальным id (первый элемент `enabled`: `enabled.get(0)` / `enabled[0]`).

## Этап 2. SchedLock и обнаружение взаимных блокировок (Deadlock)

На этапе 1 потоки обращались только к `Shared`, и каждое такое обращение проходило через `Scheduler` (в `withdraw-v0` лока нет). В `withdraw-v1` и `transfer` баланс — обычное поле под локом. Если взять стандартный `std::mutex` или `synchronized`, планировщик ничего о нём не узнает, для обхода этого пишем `SchedLock` (в C++ `sched_mutex`).

### Реализация SchedLock (`sched_mutex`)
`SchedLock` не блокирует поток в ОС. Он взаимодействует с `Scheduler`:
- `lock()`: если замок свободен, занять его и назначить владельца. Если замок занят: пометить текущий поток как заблокированный на этом замке, отдать ход планировщику. Пока замок занят, поток не попадает в список `enabled`.
- `unlock()`: освободить замок, уведомить планировщик (ожидающие потоки становятся кандидатами на пробуждение).
- **Deadlock:** если в системе остались живые потоки, но список `enabled` пуст — наступил взаимный тупик. Планировщик мгновенно фиксирует это без тайм-аутов (в `held` только занятые локи, в порядке создания):
  ```
  DEADLOCK held={a:A, b:B}
  ```
- **После deadlock** застрявшие потоки спят на своих семафорах навсегда. Их нужно разбудить и завершить (например, флаг «прогон прерван» + исключение, которое раскручивает стек потока). Иначе `run()` повиснет на `join`, а в C++ разрушение незавершённого `std::thread` вызовет `std::terminate`.
  - C++: деструктор `sched_guard` вызывает `unlock()` и во время этой раскрутки. Если `unlock()` тогда бросит исключение, будет `std::terminate`: после прерывания прогона `unlock()` должен тихо выходить.
  - Раскручиваемые потоки не должны писать в общий `log`: они идут параллельно, и TSan увидит гонку.

Чтобы увидеть deadlock, нужно задать плохое расписание руками. Для этого стратегия `Replay(trace)`: проигрывает записанную трассу, на i-м решении выбирает поток `trace[i]` (`A` → 0, `B` → 1). В `beginRun()` сбрасывает позицию. Если поток из трассы сейчас не в `enabled` или трасса кончилась раньше прогона, это ошибка трассы: бросайте исключение (если трасса длиннее прогона, лишние буквы игнорируются). Runner его не ловит: на неверной трассе (например, `withdraw-v1 replay AABB`) программа завершится со стектрейсом / `terminate` и вашим текстом ошибки. Это ожидаемо, а не падение планировщика.

## Этап 4. Полный перебор (DFS)

**Что написать:** стратегию `Dfs(bound)`. Ограничение `bound` понадобится на этапе 5, сейчас runner для `dfs` передаёт максимум (`Integer.MAX_VALUE` / `INT_MAX`).

Random пробует случайные расписания: одно и то же может попасться много раз, а нужное — ни разу. DFS, в свою очередь, рассмотрит все варианты.

Если DFS не нашёл ни одного плохого расписания, значит, ни один порядок шагов программу не ломает. Но, это верно только для тех точек паузы, которые расставлены в коде. Баги другого рода, например переупорядочивание записей процессором, DFS не проверяет.

### Как обойти дерево
Каждый прогон запускается с нуля (теоретически возможно конечно делать snapshot состояния в точке, а потом возвращаться к нему, чтобы не делать перезапуск, а "откатываться в предыдущее состояние", но практически -- нельзя, поэтому так), а DFS запоминает только, какие выборы сделал в прошлый раз.

Варианты на развилке перебираются по порядку: A, B, C. Поэтому первая плохая трасса у вас совпадёт с эталоном.

Прогон может кончиться раньше остальных (deadlock в `transfer`: трасса `AB` короче). Тогда путь в дереве тоже короче: развилки, до которых прогон не дошёл, в нём не хранятся.

```
                 развилка 1
             A ┌──────┴──────┐ B
          развилка 2     развилка 2
          A ┌──┴──┐ B     A ┌──┴──┐ B
            …     …         …     …

 прогон 1:  A A …         везде первый вариант
 прогон 2:  A B …         повторили «A», на развилке 2 взяли B
 прогон 3:  B A …         на развилке 2 всё попробовано → на развилке 1 взяли B
 прогон 4:  B B …
```

## Этап 6. Коллектор метрик

В лабораторной 1 вы реализовывали алгоритм двойной буферизации: писатели инкрементируют корзины в буфере `active`, а читатель `snapshot()` переключает `active` на противоположный буфер, ждёт выхода писателей из старого буфера и забирает его данные.

```
                    active = 0 (пишем в буфер 0)
               ┌──────────────────────┐
Поток W ──►    │ Буфер 0  |  Буфер 1  │   inside = 0 (пишу в буфер 0)
               └──────────────────────┘
                     ▲
                     │ Читатель переключает active = 1
                     ▼
Поток W ──►    начинает писать в Буфер 1
Читатель R ──► ждёт inside != 0, забирает Буфер 0 и обнуляет его.
```

В этой лабораторной коллектор уже дан в готовом виде (`Targets.java` / `targets.hpp`). Он упрощён по сравнению с первой работой:
1. Вместо 256 корзин и полей `sum/min/max` оставлен ровно один счётчик на буфер `cnt[w][b]`. Окно гонки от корзин не зависит, а каждое лишнее поле порождает дополнительные точки переключения. Без этого упрощения DFS не обошёл бы дерево даже для одного вызова `record()`.
2. Читатель ожидает писателей через `await(inside[w] != old)`, а не через активный spin-loop: spin-loop в нашем детерминированном планировщике породил бы бесконечную ветку.

Алгоритм тестовой программы:
```
record(w):  loop { b = active; inside[w] = b;
                   if (no step 3 || active == b) break;   // step 3: re-check
                   inside[w] = -1; }
            cnt[w][b] = cnt[w][b] + 1;  inside[w] = -1

snapshot(): old = active; active = 1 - old;
            for each w: await(inside[w] != old)           // ждём ухода писателя из old
            for each w: global += cnt[w][old]; cnt[w][old] = 0

проверка:   global + оставшиеся cnt == writers * n, иначе "LOST k record(s)"
```

Все разделяемые переменные (`active`, `inside`, `cnt`) обёрнуты в `Shared`: перед каждым обращением к ним стоит пауза, как у любого `Shared`. Потоки именуются буквами по порядку: сначала писатели (`A`, `B`…), последним — читатель. В именах переменных в логе писатели нумеруются с единицы: `inside[W1]` — это писатель, который в трассе идёт как `A`.

`await(cond)` подчиняется тем же правилам паузы, что `Shared` и `SchedLock` (раздел «Где Scheduler ставит паузу» в этапе 1). Пауза перед ним ставится, если с прошлой паузы поток трогал общее состояние или если `cond` сейчас ложно. Во втором случае поток ждёт и не попадает в `enabled`, пока условие не выполнится. Когда условие стало истинным, `await` пишет в лог `await done` и, как `point()`, требует паузу перед следующей операцией. Ошибка в этом правиле не меняет числа этапов 1–5: разница видна только на контрольной точке этапа 6.

Формат имени тестовой программы: `collector-<variant>-<writers>x<n>`.
Например, `collector-nostep3-1x2` — вариант `nostep3`, 1 писатель, 2 вызова `record()`.

## Этап 7. Модели памяти процессора (mini-jcstress и Store Buffering)

На этапе 6 конфигурация `collector-acqrel-1x1` содержит ошибку: рукопожатие Деккера (писатель пишет `inside` и читает `active`, читатель пишет `active` и читает `inside`) требует `seq_cst`, а с `release/acquire` два потока могут зайти в один буфер одновременно. Но наш DFS показал 0 ошибок.

Вопрос этапа: проявляется ли эта ошибка на реальном процессоре? Чтобы проверить это, выделим суть рукопожатия в минимальную тестовую программу.

### Тест Store Buffering (SB)

Два потока обращаются к двум переменным (начальные значения $x = 0, y = 0$):

```
Поток 1:  x = 1;  r1 = y;
Поток 2:  y = 1;  r2 = x;
```

Возможные исходы $(r1, r2)$:
- `(0, 1)` — Поток 1 выполнился целиком до Потока 2.
- `(1, 0)` — Поток 2 выполнился целиком до Потока 1.
- `(1, 1)` — шаги потоков перемешались.
- `(0, 0)` — оба потока не увидели запись соседа.

При последовательной согласованности (`seq_cst`) исход `(0, 0)` невозможен: любой порядок четырёх операций ставит хотя бы одну запись раньше чтения в другом потоке.

Но на x86 у каждого ядра есть store buffer:

```
Ядро 1                              Ядро 2
┌───────────┐                       ┌───────────┐
│  x = 1    │                       │  y = 1    │
└─────┬─────┘                       └─────┬─────┘
      ▼                                   ▼
[store buffer 1]                    [store buffer 2]
      │   чтение r1 = y                   │   чтение r2 = x
      │   (из L1/L2 кэша: y ещё 0)        │   (из L1/L2 кэша: x ещё 0)
      ▼                                   ▼
═════════════════════════════════════════════════
                 L1 / L2 кэш
═════════════════════════════════════════════════
```

Запись сначала попадает в store buffer своего ядра и лишь позже сбрасывается в кэш. Последующее чтение другой переменной успевает выполниться раньше из кэша. В результате оба ядра читают старые нули, и исход `(0, 0)` физически происходит на железе.

Связь с лабораторной 1: это ровно рукопожатие Деккера из коллектора метрик. Писатель пишет `inside`, затем читает `active`. Читатель пишет `active`, затем читает `inside`. Исход `(0, 0)` означает, что оба не заметили запись соседа и оказались в одном буфере.

### Как устроен mini-jcstress

Программа уже готова: для Java это `src/lab2/MiniStress.java`, для C++ — `extra/ministress.cpp`. Писать её с нуля не нужно.

В программе выделены четыре массива размером в `cells` ячеек: `x[]`, `y[]`, `r1[]`, `r2[]`.
Работа разбита на раунды (`rounds`):
1. Главный поток и оба рабочих встречаются на барьере `go`.
2. Рабочие потоки стартуют одновременно и бегут циклом по всему массиву без какой-либо синхронизации между итерациями:
   - Поток 1: `x[i] = 1; r1[i] = y[i];` для всех $i$ от $0$ до $\text{cells} - 1$.
   - Поток 2: `y[i] = 1; r2[i] = x[i];` для всех $i$ от $0$ до $\text{cells} - 1$.
3. Потоки отмечаются на барьере `done`.
4. Главный поток обходит результаты раунда, по каждой ячейке $i$ увеличивает счётчик исхода в гистограмме и сбрасывает `x[i] = y[i] = 0`.
5. Цикл повторяется `rounds` раз.

Зачем пачка (`cells`): без неё пришлось бы ставить барьер вокруг каждой пары операций, и почти всё время уходило бы на барьеры. Так устроен режим `naive`. Пачка даёт потокам бежать без синхронизации; этот же приём использует настоящий jcstress. Как часто при этом выпадает `(0, 0)`, зависит от размера пачки, способа старта потоков, языка и машины: в наших прогонах зависимость была разной в Java и C++, и `naive` где-то почти гасил эффект, а где-то нет.

Режимы работы:
- **C++:** `relaxed`, `acqrel`, `seqcst`, `naive` (`std::atomic` с `memory_order` в параметре шаблона).
- **Java:** `plain`, `acqrel` (`VarHandle setRelease` / `getAcquire`), `volatile` (`setVolatile` / `getVolatile`), `naive`.

Параметры запуска: `<mode> <rounds> <cells>`. У `naive` ячейка всегда одна, а третий аргумент умножает число раундов: `naive 200000 1` — 200 000 раундов по одной паре.
- **C++:**
  ```bash
  ./ministress relaxed 2000 10000
  ./ministress acqrel 2000 10000
  ./ministress seqcst 2000 10000
  ./ministress naive 200000 1
  ```
- **Java:**
  ```bash
  java -cp out lab2.MiniStress plain 2000 10000
  java -cp out lab2.MiniStress acqrel 2000 10000
  java -cp out lab2.MiniStress volatile 2000 10000
  java -cp out lab2.MiniStress naive 200000 1
  ```

Пример вывода (Java `volatile 200 10000`):
```
mode=volatile samples=2,000,000
  (0,0)              0    0.000%  forbidden under seq_cst
  (0,1)      1,189,383   59.469%
  (1,0)        805,708   40.285%
  (1,1)          4,909    0.245%
```

В таблицу режимов проценты указывать не требуется: они зависят от частоты процессора, загрузки ядер и таймингов запуска потоков. Важен только факт: появился исход `(0, 0)` или нет. Проценты нужны только в таблице «Размер пачки» (задание 7.1). Если вывод показывает `0.000%`, смотрите на абсолютное число случаев: даже один — это «есть».

> **Ловушка C++:** в `extra/ministress.cpp` порядок `memory_order` передан как параметр шаблона. Если передать его обычной переменной времени выполнения, компилятор GCC сгенерирует код под самый строгий барьер (`seq_cst`), и исход `(0, 0)` исчезнет во всех режимах.

### Итог

Наш планировщик перебирает варианты чередования инструкций (interleaving), но не видит аппаратных переупорядочиваний процессора. Аппаратные эффекты проявляются только на реальном железе (jcstress, mini-jcstress) либо в верификаторах со встроенной моделью памяти. Lincheck в режиме model checking также опирается на последовательно согласованную модель (`seq_cst`). Именно поэтому разные инструменты занимают разные ступени в тестировании конкурентного кода.

### 3. Результаты этапа 6 (Коллектор)

| Программа | Расписаний | Ошибок | Первая ошибочная трасса | Почему DFS видит / не видит баг |
|---|---|---|---|---|
| `collector-nostep3-1x1` | 112 | 12 | `ABBBAABAAB` | Читатель снимает снапшот до того, как писатель попал обеими фазами в один буфер, и запись теряется. |
| `collector-plain-1x1` | 29 | 0 | - | `inside` — обычное поле `int`, а не `Shared` |
| `collector-acqrel-1x1` | 972 | 0 | - | Планировщик работает в последовательно согласованной модели и не моделирует store buffer. |
| `collector-ok-1x1` | 972 | 0 | - | все норм. |

- **Потеря записи**: Писатель `A` и читатель `B`, стартовый буфер `active=0`:
```
A active->0          # A прочитал active=0 -> b=0 (запомнил старый буфер)
B active->0          # B прочитал active=0 -> old=0
B active=1           # B переключил active=1
B await done         # B ждёт inside != 0; inside пока -1 (писатель ещё не входил) -> сразу прошёл
A inside=0           # A "входит" в буфер 0 (записывает по запомненному b)
A cnt[W1][0]->0      # A читает счётчик (=0)
B cnt[W1][0]->0      # B уже списывает старый буфер: читает cnt=0, значит записи ещё нет
A cnt[W1][0]=1       # A записывает 1
A inside=-1          # A вышел
B cnt[W1][0]=0       # B обнуляет cnt (затирает записанную A единицу)
```

- **Почему одного писателя с одним вызовом оказалось достаточно?** Потеря записи здесь — это несогласованность читателя-писателя: писатель успел прочитать `active` до переключения и не увидел его после. 
- **Почему `collector-plain-1x1` даёт 0 ошибок при наличии бага?** Перебор DFS идёт только по точкам паузы. В `plain` поле `inside` — обычный `int` без `Shared`, пауз вокруг него нет, поэтому опасное чередование в дереве просто не представлено. Наш код должен быть нормально проинструментирован, а здесь это не выполняется. 
- **В чём разница между нулём у `acqrel` и нулём у `ok`?** У `ok` ноль означает корректность: шаг 3 + `seq_cst` + await - нарушений нет по построению. У `acqrel` ноль - ограничение модели acquire-release: планировщик исполняет всё в последовательно согласованной модели.

**Ответы на вопросы этапа 7.**
- Почему `(0,0)` появляется в `acqrel`, хотя на этапе 6 DFS дал 0 ошибок на `collector-acqrel-1x1`? DFS перебирает только чередования операций и не моделирует саму модель acquire release. 
- Режим `naive` тестирует операции по одной, из-за чего накладные расходы на барьеры между раундами огромны. Тем не менее на моей машине все случилось так, что  ядра всё равно успевали читать старые значения из кэша до сброса Store Buffer, из-за чего исход (0,0) проявился. Пачечный же режим (с cells=100 и 100000) позволяет потокам "разогнаться" внутри одной пачки без барьеров, из-за чего частота выпадения эффекта Store Buffering сильно зависит от размера пачки: чем меньше пачка, тем кучнее потоки идут по ячейкам, увеличивая вероятность зафиксировать (0,0).
